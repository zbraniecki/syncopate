# Rust schedulers to compare against

| Crate | Overlap with my crate’s features | How it works |
|------|-----------------------------------|--------------|
| Raw `tokio::time` (sleep / interval) | Periodic relative and one-shot relative scheduling; can emulate anchored schedules with `interval_at` / computing `Instant` from wall-clock. No runtime-agnostic `tick()`, no explicit coalescing windows, no priorities; only per-timer `MissedTickBehavior` for intervals.[web:5] | Tokio exposes `sleep`, `sleep_until`, `interval`, and `interval_at`, all backed by a single hierarchical timer wheel in the runtime. Each timer or interval computes its own next `Instant` and registers it in the wheel; the runtime always sleeps until the earliest deadline and then fires all timers in that bucket. This is the baseline “one Tokio timer per job” approach your meta-scheduler would sit on top of.[web:5][web:37][web:35] |
| `rcron` | One-shot and cron-style (anchored) jobs; conceptually similar to your `tick()` + `schedule_next_tick()` idea because it exposes `time_till_next_job()` and a `tick()`-like API. Does not have cross-task coalescing windows, priorities, or rich miss semantics.[web:6] | A simple cron-like job scheduler. You register jobs with cron expressions, then drive it from your own loop: call `time_till_next_job()` to get a `Duration` to sleep, then call `tick()` (or equivalent) to execute any due jobs. Typical usage is `loop { sleep(time_till_next_job()); tick(); }`, making it runtime-independent but polling-based.[web:6] |
| `clokwerk` | Anchored periodic jobs (time-of-day, day-of-week) and simple periodic relative schedules via a fluent DSL. Similar spirit to your scheduler in that the caller owns the loop and timing (manual `run_pending()`), but it lacks a precise `next_deadline` API, coalescing windows, and priority-aware snapping.[web:60][web:99] | Synchronous job scheduler with a builder-style API such as `.every(10.minutes()).plus(30.seconds())`, `.every(1.day()).at("3:20 pm")`, and day-of-week schedules. You either call `run_pending()` in your own `loop { run_pending(); sleep(poll_interval); }` or use `watch_thread(Duration)` which spawns a background thread to poll at a fixed interval. Jobs that are due at a given poll are executed in simple iteration order.[web:60][web:99] |
| `schedule-rs` | Cron-like periodic anchored tasks similar to your OneTime/Periodic Anchored. Shares the idea of a central scheduler you drive from a loop, but again without explicit drift windows or priorities.[web:100] | In-process cron scheduler: you register jobs with cron expressions like `"0 0 * * *"` and repeatedly call `run_pending()` to execute any due jobs. Typical usage shown in docs is a loop that calls `run_pending()` and then sleeps for a fixed duration (e.g., 500 ms), so the effective resolution and drift depend on that polling interval.[web:100] |
| `job_scheduler` | Cron-based anchored jobs; overlaps with OneTime/Periodic Anchored semantics. No runtime-agnostic `next_deadline`, no window-based coalescing, and no priorities.[web:98] | A straightforward cron job scheduler. You create a `JobScheduler`, add `Job`s with cron expressions and closures, and call `tick()` in a loop. Examples usually show `loop { scheduler.tick(); sleep(Duration::from_millis(500)); }`. The scheduler checks all jobs each tick to see which should run; wakeup frequency and drift are tied to the tick interval.[web:98][web:9] |
| `tokio-cron-scheduler` | Cron-like anchored periodic jobs and one-shot jobs on Tokio. Overlaps heavily with your anchored types but is Tokio-specific and per-job-timer based. No explicit cross-task windowing or priority; miss behavior is mostly implicit via underlying timers and cron calculations.[web:12][web:17] | A `JobScheduler` holds many `Job`s, each with a cron expression or duration-based schedule. The scheduler computes next run times using cron parsing and uses Tokio timers (e.g., `sleep` or small intervals) to wait until jobs are due. A background async task drives this loop, spawning each job onto the Tokio runtime when its next time arrives. Integration features include hooks, persistence, and NATS support, but scheduling is still “each job has its own next exact instant.”[web:12][web:17] |
| `tokio-beat` | One-shot and periodic (cycle) timers on Tokio, including cron-like schedules; conceptually close to your design as a central meta-scheduler. Still Tokio-dependent and time-ordered only: no declared jitter windows or priorities driving cross-task wakeup coalescing.[web:64] | Provides a `Timer` enum (`Cron`, `Oneshot`, `Cycle`) and `Job` structures whose schedules are turned into `TimeEvent { job_id, when }` entries. These events are stored in a `BinaryHeap<Reverse<TimeEvent>>` so the earliest `when` is always at the top. A background async task repeatedly pops the earliest event, sleeps until `when`, runs the job, and pushes the next `TimeEvent` for that job. All timing is via Tokio and based on exact scheduled instants.[web:64] |
| `periodically` | Overlaps strongly on the *kinds* of schedules: one-shot, periodic relative, cron/anchored, and backoff. It is a central scheduler for many tasks, but tied to Tokio for execution, and its schedules produce exact next instants without an explicit coalescing window or priority-aware snapping.[web:59] | Defines a `Scheduler` that manages `Task` and `AsyncTask`s along with `Schedule` implementations (`IntervalSchedule`, `OneShotSchedule`, `CronSchedule`, `BackoffSchedule`, etc.). Each schedule computes its own next time based on current time and previous outcomes, including panics. A Tokio-based backend (`Scheduler::tokio_scheduler`) drives the execution by waiting on the combined next deadline and then running tasks. It’s a flexible, high-level scheduler but still per-task-timer in spirit.[web:59] |
| `tokio-task-scheduler` | Tokio-specific scheduler supporting interval, cron, and delayed tasks. Overlaps on the same four categories of jobs (one-shot, periodic, anchored vs relative), but again without a runtime-agnostic tick API, explicit windows, or priorities.[web:97] | A crate advertised as an async task scheduler for Tokio that lets you schedule tasks using cron expressions, intervals, and delays. It internally manages a set of scheduled tasks and leverages Tokio timers to fire them. Public descriptions emphasize non-blocking operation and ergonomic APIs rather than low-level wakeup optimization or cross-task coalescing.[web:97] |
